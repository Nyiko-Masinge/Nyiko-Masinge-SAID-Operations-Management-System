# Production recovery plan — activation and rehearsal pending

This is a preparation plan for NFR reliability. No production backup, restore, failover or recovery-time claim is made. Local emulator resets are disposable test preparation and are not production recovery evidence.

Keep Firebase on Spark with no payment method. Managed backups, point-in-time recovery and provider export/import features requiring billing are not activation prerequisites and must not be enabled for this release. The earlier managed-backup proposal is superseded by the zero-billing constraint. The authorized operator must agree retention and recovery targets and a Spark-compatible recovery procedure before claiming operational recovery readiness; no custom backup service or production rehearsal is implemented here. See [Firestore quotas and paid features](https://firebase.google.com/docs/firestore/quotas) for provider limits.

Retain source SHA, lockfiles, deployed rules/indexes, trusted Next API and Vercel configuration in the release record. Firestore backups do not replace separate rule/configuration recovery. Record the authorized Auth identity recovery/export process separately: Firestore employee documents must continue to match actual Auth UIDs. Keep keys and account export material outside this repository with restricted access. An EAS APK must be associated with its source SHA and Firebase environment.

Rehearse restoration into an isolated supported recovery database/project using the provider's documented destination restrictions. Do not overwrite the live database as a rehearsal. Validate roster roots and pointers, immutable version/items, employees/roles/locations/templates, progress, operational events, historical notification jobs (if present) and recipient inboxes. Check UID relationships, retained reasons/timestamps, archive flags, actor provenance and read-state preservation. Test authorized reads and denied staff cross-account writes with recovery rules before any client can reach that database. Recovery database routing and safe trusted API activation require an explicit reviewed runbook; the current SDK default-database configuration does not automatically select a restored named database.

Record observed duration and recoverable data timestamp, compare them with the agreed targets, and document failures. Cutover requires a reviewed route/credential change, restored rules/index readiness, controlled trusted API activation, authenticated cross-app smoke tests and a rollback route. Before retrying recovered progress/publication actions, confirm deterministic event/inbox IDs preserve delivered read state. Retained historical jobs do not activate retired Functions. Stop or isolate failed writers while investigating an incident; retain committed operational evidence rather than deleting it.

The release ledger must retain the real rehearsal evidence and operator approval before claiming operational recovery readiness. This plan is documentation only; production backup configuration and rehearsal remain **DEPLOYMENT PENDING**.
